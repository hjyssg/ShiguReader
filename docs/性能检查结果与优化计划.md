
## 性能检查结果与优化计划

我已经完整审查了项目代码，以下是按 PERFORMANCE_GUIDLINE.md 的 5 个检查点发现的实际问题：

---

### 🔴 问题 1：N+1 查询 — `authors.py`

`read_authors` 中获取每个作者的最新文件缩略图时，在循环里逐个查询：

```python
# authors.py — _query_once() 内
for author_name, _ in page_rows:
    latest_stmt = (
        select(File.filepath)
        .join(FileArtist, FileArtist.filepath == File.filepath)
        .where(FileArtist.artist_name == author_name)
        .order_by(File.mtime.desc())
        .limit(1)
    )
    latest_filepath = session.exec(latest_stmt).first()  # ← 每个作者一次查询
```

`page_size=24` 时就是 24 次额外 SQL。而 `tags.py` 已经用 `ROW_NUMBER() OVER (PARTITION BY ...)` 窗口函数一次搞定了。

修复方案：照搬 `tags.py` 的窗口函数写法到 `authors.py`。

---

### 🔴 问题 2：阻塞 event loop — `fs.py` 的 `list_directory`

`list_directory` 是 `async def`，但内部全是同步阻塞操作：

```python
@router.get("/list", response_model=ListResponse)
async def list_directory(...) -> ListResponse:
    dir_stat = validated_path.stat()           # 同步 I/O
    for entry in validated_path.iterdir():     # 同步遍历
        stat = entry.stat()                    # 每个文件同步 stat
        if entry.is_dir(): ...                 # 同步判断
    with get_index_session() as session:       # 同步 DB 查询
        repo.get_file_data_by_folder(...)
        repo.get_archive_metas_by_folder(...)
```

这会直接阻塞 FastAPI 的 event loop，其他请求全部排队等待。

修复方案：将整个同步逻辑包装到 `asyncio.to_thread()` 中，或者把函数改为普通 `def`（FastAPI 会自动放到线程池执行）。

同样的问题还存在于：`move_file`, `move_folder`, `delete_path`, `zip_folder`, `rename_path`, `unzip_archive`, `backfill_directory` 等多个 async 端点。

---

### 🔴 问题 3：阻塞 event loop — `search.py`

```python
@router.post("", response_model=SearchResponse)
async def search_files(body: SearchRequest) -> SearchResponse:
    with get_index_session() as session:       # 同步 DB
        repo.search_files(q, body.mode)        # 同步查询
        repo.search_by_author(q, body.mode)    # 同步查询
        repo.search_by_tag(q, body.mode)       # 同步查询
```

修复方案：同上，改为 `def` 或用 `asyncio.to_thread()`。

---

### 🟡 问题 4：`repository.py` 的 `save_parse_result` 循环 DB 查询

单条保存时每个 author/tag 都做 `session.get()` 检查：

```python
if authors:
    for author_name in authors:
        if not self.session.get(Artist, author_name):   # 每个作者一次 DB
            self.session.add(Artist(artist_name=author_name))
        if not self.session.get(FileArtist, fa_key):    # 每个作者又一次 DB
            self.session.add(FileArtist(...))
```

不过 `batch_save_parse_results` 已经用批量 IN 查询优化过了，`save_parse_result` 只在 backfill 单文件时调用，影响较小。可以优化但优先级低。

---

### 🟢 问题 5：前端大列表虚拟化

`FileViewContainer.tsx` 中 grid/mixed/details 视图都是直接 `.map()` 渲染全部 items，没有虚拟化。但这个列表是单目录内容（通常几十到几百项），不是全库搜索结果，实际影响不大。

搜索结果 (`search.py`) 目前没有分页，如果搜索结果很多可能会有问题，但前端渲染侧目前可接受。

---

## 优化计划（按优先级排序）

| 优先级 | 文件 | 问题 | 修复方式 |
|--------|------|------|----------|
| P0 | `authors.py` | N+1 查询 | 用窗口函数替代循环查询，参照 `tags.py` |
| P0 | `fs.py` 多个端点 | async 中同步阻塞 | `list_directory` 和其他文件操作端点改为 `def`（让 FastAPI 自动线程池） |
| P0 | `search.py` | async 中同步 DB | 改为 `def` |
| P2 | `repository.py` | `save_parse_result` 循环查询 | 低优先级，batch 版本已优化 |
| P2 | 前端列表 | 无虚拟化 | 当前数据量可接受，暂不改 |

实际需要改动的文件只有 3 个：`authors.py`、`fs.py`、`search.py`。
