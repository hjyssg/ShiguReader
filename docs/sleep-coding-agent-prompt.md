# 睡前交给 Coding Agent 的 Prompt（Code Review + 可维护性重构）

你是本项目的高级审查与重构工程师。请在**不做环境搭建、不做大规模重写**的前提下，完成一次“以可维护性为中心”的代码审查与小步重构。

## 项目上下文（必须遵守）
- 项目是单仓：前端 `React + Vite + Tailwind`，后端 `FastAPI + SQLModel`。
- 优先做**小步、可回滚、低风险**改动；避免“全量翻新”。
- 不要额外引入复杂基础设施；不要改变现有产品行为。

## 本次任务目标（按优先级）

### P0：Tailwind 长 className 语义化（前端重点）
请重点检查 Explorer / Reader / 共用 UI 组件中“超长 Tailwind className 串”的可读性问题，并做语义化重构：
1. 抽取语义化类名（例如 `explorer-card`, `reader-toolbar`, `file-grid-item` 等）到合适的样式文件。
2. 组件内保留少量状态类（如 `data-[state=open]`、`aria-*` 相关）即可，避免大段视觉样式堆在 JSX 里。
3. 优先重构“层级深 + 重复高 + 阅读负担重”的节点，不要一口气全仓替换。
4. 保证视觉效果不变，交互不变。

### P0：后端 Code Coverage 可维护
后端不是单次“刷覆盖率”，而是建立可持续机制：
1. 识别本次改动涉及的后端模块，补齐对应单测（正向 + 至少 1 个边界/异常路径）。
2. 覆盖率要能被持续跟踪：在现有测试脚本/命令基础上给出可复用的执行方式与阈值建议。
3. 避免无意义测试（只测 getter/setter）。优先测：
   - 文件处理边界（空输入、坏文件、编码/路径异常）
   - API 参数校验与错误响应
   - 索引/仓储层关键分支

### P1：通用可维护性重构
1. 降低超长函数和“隐式耦合”：提取小函数、明确命名、减少魔法值。
2. 为复杂业务流补“解释性注释”（解释“为什么”，不是“做了什么”）。
3. 保持类型/接口清晰：前端 props 与后端 schema 变更要同步检查。
4. 不做与任务无关的大规模目录迁移。

## 执行流程要求
1. 先做审查清单，再动代码：
   - 列出 Top N（建议 5~10）个最影响维护性的点，附文件路径与原因。
2. 再做最小改动实现：
   - 每个改动说明“收益 / 风险 / 回滚方式”。
3. 最后给验证结果：
   - 前端：lint/build/关键页面冒烟
   - 后端：测试 + coverage 汇总（含新增/受影响模块）

## 输出格式（严格按此结构）

### 1) Review Findings
- [严重级别] 文件路径：问题描述
- 为什么影响维护性
- 建议方案（1~2 行）

### 2) Refactor Plan
- 改动项 A：目标、涉及文件、风险、回滚方式
- 改动项 B：目标、涉及文件、风险、回滚方式

### 3) Implemented Changes
- 逐条列出已完成改动（按文件归类）
- 标注是否影响 UI / API / 数据结构

### 4) Verification
- 执行命令与结果（通过/失败）
- 覆盖率结果与说明
- 若有未完成项，写清阻塞原因与下一步建议

## 边界与禁区
- 禁止“顺手”改动无关模块。
- 禁止为追求覆盖率而写脆弱测试。
- 禁止在未说明风险的情况下改公共基础组件接口。

## 完成标准（Definition of Done）
- 前端至少完成一批“长 className → 语义化类名”的落地改造（可读性显著提升）。
- 后端本次改动相关代码有新增/改进测试，coverage 可被持续追踪。
- 输出包含：问题清单、改动说明、验证命令、风险与回滚方案。
