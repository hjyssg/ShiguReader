## 如果从头开始，我会这样设计 ShiguReader

### 一、当前架构的核心问题

在给方案之前，先说清楚我看到的真正问题：

**后端**
1. **"浏览即扫描"的隐式副作用**：`listDirectory` 每次被调用都会在后台触发 `upsertFile` / `saveParsedMetadata` / `markMissingInFolder`。这是一个读操作里藏着写操作，调试困难，也会在高频浏览时产生大量无意义的 DB 写入。
2. **内存状态不可持久化**：`scanStatusMap`（扫描进度）和 `inProgress`（解压状态）都是进程内 Map，服务重启后全部丢失，前端会看到"扫描消失了"。
3. **后台任务用 `setImmediate` 链**：没有真正的任务队列，无法限速、无法重试、无法查看队列深度，`backfill` 里的缩略图生成是完全 fire-and-forget 的。
4. **`thumbService` 重复了 `archiveService` 的 7z 列表解析逻辑**：两处都有解析 `Path = ...` 的代码，应该复用。
5. **`recService` 的内存缓存需要手动刷新**：`refreshRecCache()` 必须在扫描完成后手动调用，容易漏。
6. **`artists` 表用 `role` 字段区分 author/coser**：语义上 author 和 coser 是不同概念，用同一张表加 role 字段会让查询变复杂。

**前端**
1. **Prop drilling**：`GalleryModeView` 接收 14 个 props，其中 `onAfterRename/onAfterDelete/onMoveSuccess` 完全可以在组件内部调用 `useNavigate()`，不需要从父级传入。
2. **`FileActionMenuItems` 的 8 个回调 props**：调用方需要把 `useFileOperationDialogs` 的所有 open* 方法逐一拆开传入，接口臃肿。
3. **没有实时推送**：扫描进度靠轮询，解压进度靠轮询，体验不如 SSE/WebSocket。
4. **`listDirectory` 的响应没有分页**：一个目录有几千个文件时，前端一次性拿到全部数据，内存和渲染都有压力。

### 二、重设计方案

#### 后端架构

**1. 严格分离"读"和"写"**

`listDirectory` 只做纯读操作，不再触发任何 DB 写入：

```
GET /api/v1/fs/listdir?path=...
  → 只读 FS + 只读 DB，返回 items
  → 不再有 setImmediate upsert

POST /api/v1/fs/scan  (显式触发扫描)
  → 写 DB，更新索引
```

"浏览时自动更新索引"这个需求可以保留，但改成前端在 Explorer 页面主动调用一个轻量的 `POST /api/v1/fs/touch-folder`，语义清晰，可以被用户感知和控制。

**2. 用 SQLite 持久化任务状态**

把 `scanStatusMap` 和 `inProgress` 从内存 Map 移到 `activity_logs` 表（已有）或新增 `jobs` 表：

```sql
CREATE TABLE jobs (
  id TEXT PRIMARY KEY,          -- uuid
  job_type TEXT NOT NULL,       -- scan / backfill / extract / compress
  target_path TEXT NOT NULL,
  status TEXT NOT NULL,         -- pending / running / completed / failed
  progress_json TEXT,           -- { scanned: 100, total: 500 }
  created_at INTEGER,
  updated_at INTEGER
);
```

服务重启后任务状态不丢失，前端可以查询历史任务。

**3. 真正的后台任务队列**

用一个简单的 `JobQueue` 类替代 `setImmediate` 链：

```typescript
class JobQueue {
  private queue: Job[] = []
  private running = 0
  private concurrency: number

  enqueue(job: Job): void
  private async runNext(): Promise<void>
}
```

所有后台任务（缩略图生成、archive meta 回填、rec score 更新）都通过这个队列执行，有并发控制、有错误重试、有进度追踪。

**4. SSE 推送任务进度**

```
GET /api/v1/jobs/:id/stream  → text/event-stream
```

前端订阅这个 SSE 流，实时收到扫描进度、解压进度，不再需要轮询。

**5. 拆分 authors/cosers 表**

```sql
-- 现在
file_artists (filepath, artist_name, role)  -- role = '' | 'coser'

-- 改成
file_authors (filepath, author_name)
file_cosers  (filepath, coser_name)
```

查询更直观，索引更高效，不需要每次都带 `AND role = ''` 条件。

**6. `listDirectory` 支持服务端分页**

```
GET /api/v1/fs/listdir?path=...&page=1&page_size=100&sort_by=mtime&sort_order=desc
```

大目录不再一次性返回全部，前端分页加载。

**7. 复用 archive entry 解析**

`thumbService` 里的 7z 解析逻辑删掉，直接调用 `archiveService.listEntries()`，消除重复代码。

#### 前端架构

**1. 消除 GalleryModeView 的 prop drilling**

`onAfterRename/onAfterDelete/onMoveSuccess` 这三个回调在 `GalleryModeView` 内部直接调用 `useNavigate()`：

```tsx
// 现在：从父级传入
onAfterRename={() => navigate({ to: "/" })}

// 改成：GalleryModeView 内部自己处理
const navigate = useNavigate()
const { openRename, dialogs } = useFileOperationDialogs({
  currentPath: parentPath,
  onAfterRename: () => navigate({ to: "/" }),  // 内部定义
})
```

`ReadPage` 不再需要传这三个回调，props 从 14 个减到 11 个。

**2. FileActionMenuItems 改为接收 filePath**

```tsx
// 现在：8 个回调 props
<FileActionMenuItems
  onRename={() => openRename(path)}
  onMove={() => openMove(path)}
  onMoveToFavorite={() => openMove(path, undefined, "favorite")}
  // ...
/>

// 改成：传 filePath + dialogs hook
<FileActionMenuItems
  filePath={path}
  isFolder={isFolderSource}
  isArchive={isArchiveSource}
  dialogs={fileOpDialogs}  // 传入 hook 返回的 openers 对象
/>
```

**3. 用 Zustand 管理全局 UI 状态**

当前项目没有全局状态管理，`isMobile`、`viewMode` 等状态在组件间靠 props 传递。引入轻量的 Zustand：

```typescript
const useUIStore = create<UIState>((set) => ({
  isMobile: false,
  setIsMobile: (v) => set({ isMobile: v }),
}))
```

`TableRowCells` 直接调用 `useUIStore(s => s.isMobile)`，不需要从 `FileTableView` 传入。

**4. 用 SSE 替代轮询**

```typescript
// 现在：轮询扫描状态
useQuery({ queryKey: ["scan-status"], refetchInterval: 2000 })

// 改成：SSE 订阅
useEffect(() => {
  const es = new EventSource(`/api/v1/jobs/${jobId}/stream`)
  es.onmessage = (e) => updateScanProgress(JSON.parse(e.data))
  return () => es.close()
}, [jobId])
```

**5. 虚拟列表**

`FileGridView` 和 `FileTableView` 在大目录下渲染几百个 DOM 节点。引入 `@tanstack/react-virtual` 做虚拟滚动，只渲染视口内的条目。

### 三、保持不变的部分

这些设计是对的，不需要动：

- **Fastify + Node.js + SQLite**：轻量、零依赖、适合本地部署，不需要换成 PostgreSQL 或 Redis
- **TanStack Router + React Query**：URL 状态管理和服务端状态管理的最佳实践
- **7z + ImageMagick 的工具链**：捆绑二进制文件的思路很好，开箱即用
- **三阶段渐进式解压**（phase1/2/3）：这个设计很聪明，保留
- **`useFileOperationDialogs` hook**：把对话框状态集中管理的思路是对的，只需要减少传入的回调数量
- **`rec_score` 的计算公式**：`log(1+Fa) + max_tag(log(1+Ft)/sqrt(Nt))` 合理，保留
- **`parseName` 的文件名解析**：从文件名提取 author/tag/event 的逻辑是核心功能，保留

---

### 四、优先级排序

如果只能做三件事：

1. **把 `listDirectory` 的隐式写操作剥离出去** — 这是最容易引发 bug 的设计，影响所有浏览操作
2. **把扫描/解压状态持久化到 DB** — 解决重启后状态丢失的问题
3. **消除 GalleryModeView 的 prop drilling** — 代码可维护性最直接的改善

其余的（SSE、虚拟列表、拆分 authors/cosers 表）是锦上添花，可以按需推进。
